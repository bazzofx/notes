## Important Note on Workspaces
### Microsoft Sentinel sharing a Log Analytics Workspace
Considering that Microsoft Sentinel workspace uses a Log Analytics workspace, you have the option to enable the Microsoft Sentinel workspace in a Log Analytics workspace that is used by other solutions. The most common scenario is sharing the Log Analytics workspace used by Microsoft Defender for Cloud. Sharing the workspace enables one central workspace to query security data.

### Microsoft Defender for Cloud
When creating your Microsoft Sentinel workspace, you aren't allowed to use the **Default** Microsoft Defender for Cloud Log Analytics workspace. You need to manually create a Log Analytics workspace then update the Microsoft Defender for Cloud tier. Now you can select the manually created Log Analytics workspace for use with Microsoft Defender for Cloud.

## Microsoft Sentinel permissions and roles
![[Pasted image 20260711150719.png]]
Microsoft Sentinel uses `Azure role-based access control (Azure RBAC)` to provide built-in roles that can be assigned to users, groups, and services in Azure.

### Microsoft Sentinel-specific roles

All Microsoft Sentinel built-in roles grant read access to the data in your Microsoft Sentinel workspace:

- **Microsoft Sentinel Reader**: can view data, incidents, workbooks, and other Microsoft Sentinel resources.

- **Microsoft Sentinel Responder**: can, in addition to the above, manage incidents (assign, dismiss, etc.

- **Microsoft Sentinel Contributor**: can, in addition to the above, create and edit workbooks, analytics rules, and other Microsoft Sentinel resources.

- **Microsoft Sentinel Automation Contributor**: allows Microsoft Sentinel to add playbooks to automation rules. It isn't meant for user accounts.

|Roles|Create and run playbooks|Create and edit workbooks, analytic rules, and other Microsoft Sentinel resources|Manage incidents such as dismissing and assigning|View data incidents, workbooks, and other Microsoft Sentinel resources|
|---|---|---|---|---|
|Microsoft Sentinel Reader|No|No|No|Yes|
|Microsoft Sentinel Responder|No|No|Yes|Yes|
|Microsoft Sentinel Contributor|No|Yes|Yes|Yes|
|Microsoft Sentinel Contributor and Logic App Contributor|Yes|Yes|Yes|Yes|

>[NOTE]
>Best practices: For best results, these roles should be assigned to the resource group that contains the Microsoft Sentinel workspace. The roles then apply to all the resources that deploy to support Microsoft Sentinel, if those resources are in the same resource group.

### Giving Microsoft Sentinel permissions to run playbooks
- Playbooks are built on Azure Logic Apps,
- Assign specific security ops team members the ability to use Logic Apps for SOAR operations.
- **Microsoft Sentinel uses a dedicated service account to run playbooks**
- **For an automation rule to run a playbook, the service account needs explicit permissions on the playbook's resource group—after which any rule can run any playbook in that group.** Granting those permissions requires Owner access to the playbooks' resource groups
### Connecting data sources to Microsoft Sentinel
For a user to add data connectors, you must assign the user `write permissions on the Microsoft Sentinel workspace.` + `other permissions for each connector.`  As listed on the relevant connector page.

### Guest users assigning incidents
If a `guest user needs to be able to assign incidents`, then in addition to the Microsoft Sentinel Responder role, the user will also need to be assigned the role of Directory Reader. This role isn't an Azure role but a Microsoft Entra role, and that regular (non-guest) users have this role assigned by default

### Creating and deleting workbooks
To create and delete a Microsoft Sentinel workbook, the user requires either the `Microsoft Sentinel Contributor role` or a lesser Microsoft Sentinel role plus the `Azure Monitor role` of Workbook Contributor. This role isn't necessary for using workbooks, but only for creating and deleting

### Azure roles and Azure Monitor Log Analytics roles
- Azure roles grant access across all your Azure resources. They include Log Analytics workspaces and Microsoft Sentinel resources:
    - Owner
    - Contributor
    - Reader
- Log Analytics roles grant access across all your Log Analytics workspaces:
    - Log Analytics Contributor
    - Log Analytics Reader

## Manage Sentinel Settings 
Sentinel settings are managed in two places: within `Sentinel (left nav > Settings, with varying tabs)` and mostly in the underlying `Log Analytics workspace`—where some data connector configs also redirect you.

Set workspace retention (30–730 days, except Free tier) in `Sentinel Settings > workspace settings > Log Analytics > Usage and estimated costs > Retention`.

## Configuring logs on Sentinel
When configuring Sentinel workspaces, plan for two data states 
- Analytics retention for real-time monitoring, 
- Long-term retention for low-cost archival, accessible via search/restores)
- three table plans, and two log tiers.

>We recommend Microsoft Sentinel data lake for secondary and long-term data storage
Microsoft Sentinel data lake provides greater scalability, flexibility, and integration for advanced security and compliance.

### Types of Logs on Sentinel
- The **Analytics** plan is suited for continuous monitoring, real-time detection, and performance analytics. This plan makes log data available for interactive multi-table queries and use by features and services for 30 days to two years.

- The **Basic** plan is suited for troubleshooting and incident response. This plan offers discounted ingestion and optimized single-table queries for 30 days.

- The **Auxiliary** plan is suited for low-touch data, such as verbose logs, and data required for auditing and compliance. This plan offers low-cost ingestion and unoptimized single-table queries for 30 days.

### Logs Convertion
>For Sentinel workspaces linked to Defender, manage tiering and retention via Defender's new table management experience. If using Basic logs, convert them to analytics tier first in Log Analytics before making changes in Defender.

### Data Tiers in Microsoft Sentinel
There are two primary tiers in Microsoft Sentinel and a default XDR tier:

- Analytics Tier
- Data lake Tier
- XDR default tier
#### Analytics tier
This tier supports alerting, hunting, workbooks, and all Sentinel features, with data retained in two states.
- Hot data tier defaults to 30 days (extendable to 2 years at a prorated monthly rate). 
- You can extend Sentinel retention period of Sentinel up to 90 days for free
#### Data lake tier
-  Low-cost "cold" tier
- Isn't available for real-time analytics
- Can access data whenever needed through `KQL jobs`[](https://learn.microsoft.com/en-us/azure/sentinel/datalake/kql-jobs)
- Analyze trends over time by running scheduled KQL or Spark jobs.
- Aggregate insights from incoming data at regular intervals using summary rules.

#### XDR default tier.
- Default location for Data on Microsoft Defender XDR
- Tier includes 30 days analytics retention + XDR license
- Data is not ingested into Sentinel Analytics or data lakes
- Data retention longer than 30 days is possible
- It is not possible to run `KQL jobs` on default XDR tier

### Managing Log Tables
We can view some tables from Microsoft Defender, but not all tables. The tables are managed from `Analytics in Sentinel` page

- Basic logs tables are viewable in the Defender portal but only manageable from Log Analytics.
- To manage them in the Defender portal, change the table plan from Basic to Analytics in Sentinel.
- We can manage tables and log retention on Microsoft Defender Portal
- `Microsoft Defender Portal>  Microsoft Sentinel > Configuration > Tables` 

**Analytics tier:**
- Analytics retention: 30 days to 2 years.
- Total retention: Up to 12 years in the data lake.
- By default, total retention equals analytics retention (no long-term retention).
- To enable long-term retention, set total retention greater than analytics retention.
- Example: 90 days analytics + 180 days total = 6 months long-term retention.

**Data lake tier:
- Retention: 30 days to 12 years.

**Tier changes:**
- You can change tiers anytime based on cost and usage needs.

**Considerations:**
- Increased retention is likely to lead to increased data cost.
- Changing from the analytics to the data lake tier causes features that rely on analytics data to stop functioning such as:
    - Alerting
    - Advanced hunting
    - Analytics rules
    - Custom detection rules

### Table Support for Basic Logs
- All Log Analytics tables default to Analytics tier.
- Only certain tables can be changed to Basic Logs.
- Tables cannot be changed if Azure Monitor relies on them for key features.
You can currently configure the following tables for Basic Logs:
- DCR-based custom logs
- ContainerLogV2 (Container Insights)
- AppTraces (Application Insights)
#### Basic Logs KQL
- Basic Logs queries use a limited KQL subset for simple data retrieval.

- Supported operators: where, extend, project, project-away, project-keep, project-rename, project-reorder, parse, parse-where.

- Unsupported: join, union, and aggregates (summarize).
